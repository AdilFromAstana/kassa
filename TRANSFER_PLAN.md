## 2. БАГ, который надо починить (корень риска)
`createStoreDoc` для ВСЕХ типов кроме инвентаризации делает `stock = stock − qty`. Для `'Внутреннее перемещение'` это:
- уменьшает общий остаток (как расход) и **ничего не добавляет на целевой склад** → перемещение МОЛЧА теряет количество;
- `buildStockMoves` показывает только расход из источника (нет прихода в приёмник) → асимметрия в ОСВ.
Сейчас не видно, т.к. один ингредиент = один склад. Как только появятся остатки по складам — всплывёт.

## 3. Дизайн (РЕШЕНО): per-store = единый источник, итог = производная
Отвергнуты: чистый A (инвазивно, риск) и оверлей-B (два источника правды → дрейф, «не логично для всех»).

**Подход: единый источник `storeStock[ingredientId][store]`; `i.stock` = кэшируемая сумма по складам.**
- **Источник правды** — остаток по складам `storeStock: Record<ingredientId, Record<store, qty>>`. Совпадает с `StockBalance` по точке в .NET-бэке → фронт↔бэк консистентны (масштабируемо).
- **`i.stock`** = Σ по складам, **пересчитывается и кэшируется на ингредиенте после КАЖДОЙ операции**. Все существующие читатели `i.stock` (продажа, low-stock, отчёты, `dishMaxPortions`, WarehouseScreen «Все склады») работают без правок и без расхождений.
- **Одна точка мутации** — хелпер `applyStockDelta(id, store, qty)` (и батч для строк документа): меняет `storeStock`, затем ресинкает `i.stock`. Никаких прямых `i.stock - qty` в обход.
- **Перемещение**: `applyStockDelta(id, from, −qty)` + `applyStockDelta(id, to, +qty)` → итог неизменен, баг «потери» исчезает.
- **Продажа/приход/инвентаризация**: переводятся на тот же хелпер с указанием склада (продажа/реализация — «домашний» склад ингредиента или склад точки; приход — склад накладной; инвентаризация — выбранный склад). Итог всегда = сумме → старый код цел.

Почему так: один источник правды (нет дрейфа), итог валиден для всего старого кода (безопасно), модель = бэкенду (масштабируемо). Истинная мультиточка/центральный склад (п.9) ложится сверху как ещё одно измерение склада/точки.
