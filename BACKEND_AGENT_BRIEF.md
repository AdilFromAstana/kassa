# BACKEND_AGENT_BRIEF.md — задание ИИ-агенту: спроектировать бэкенд из мока

> **Кому:** ИИ-агенту-разработчику (или человеку), который спроектирует и опишет бэкенд для iiko-style POS (Казахстан).
> **Главная идея:** **мок — это и есть спецификация.** Все сущности, поля, связи и «таблицы» уже формализованы в коде. Не надо «прокликивать админом» — модель данных извлекается из исходников. Прокликивание нужно только для приёмочной проверки флоу и скриншотов (опционально).

---

## 0. Контекст
- Это **рабочий фронтенд-мок** кассы + бэк-офиса iiko (React + Zustand + localStorage). Все экраны и бизнес-флоу работают.
- Контекст — **Казахстан (РК):** валюта тенге ₸, **ҚҚС 16%**, идентификатор **БИН/ИИН**, фискализация **Webkassa / ОФД РК**, документооборот **ЭСФ/СНТ** (esf.gov.kz), типовой **план счетов РК**, выгрузка в **1С:Бухгалтерия для Казахстана**.
- Цель бэкенда: фронт подключается к нему **без переписывания UI** через готовый слой `src/api/` (см. ниже). Стек бэка — **.NET**, БД по умолчанию — **PostgreSQL** (агент может обосновать иное).

## 1. Где «истина» (читать в первую очередь, именно эти файлы)
1. **`src/types.ts`** — все доменные типы/интерфейсы. Это **схема сущностей** (поля, типы, enum-значения, обязательность через `?`).
2. **`src/store/pos.ts`** — состояние + действия. Здесь:
   - функции `load*/persist*` и ключи `localStorage` = **границы хранения** (= таблицы/агрегаты);
   - константа `RUNTIME_KEYS` = **операционный (транзакционный) слой**;
   - actions (`pay`, `closeCashShift`, `refundOrder`, `addPurchase`, `createStoreDoc`, …) = **операции = кандидаты в доменные API-эндпоинты**.
3. **`src/api/CONTRACT.md`** + `src/api/contract.ts` — **уже описанная граница**: `config/:key` (справочники/настройки) vs `runtime` (операционные данные смены) + перечень всех ключей. **Контракт `PosRepository` менять нельзя** — фронт на него опирается.
4. **`src/mock/data.ts`, `src/mock/warehouse.ts`, `src/mock/menu.ts`** — сид-данные = **примеры строк и реальные связи** (FK видны по `id`-полям: `dishId`, `ingredientId`, `staffId`, `supplierName/Id`, `loyaltyCardId`, `tableId/hallId`, `discountId`, `courierId`, …).
5. **`src/lib/*`** — это **НЕ таблицы, а бизнес-логика** (чистые функции): `stockMoves` (журнал движений + остатки), `ledger` (двойные проводки РК), `pivot` (OLAP), `payables` (задолженность/статусы оплаты), `planfact`, `schedule`, `quickMenu`, `loyalty`, `rights`, `money`, `export`. **Решить по каждой: считать на сервере или оставить на клиенте.**
6. **`src/lib/rights.ts`** — каталог прав (`F_*` касса / `B_*` офис / `D_*` доставка), `POSITION_RIGHTS`, 8 ролей → **основа RBAC/авторизации**.
7. Доп. контекст по экранам/процессам — `../iiko_spec/` (реверс iiko, topic-* + скрины) и `PARITY_GAP.md` (что реализовано).

## 2. Что код уже даёт «бесплатно» (не переоткрывать)
- **Чёткое разделение слоёв:**
  - **Reference / config** (медленно меняется): заведение, меню/цены/прейскурант, склад/техкарты, справочники (сотрудники/оплаты/заказы/списания/смены), права, дисконт, лояльность (программа/карты/акции/депозит/сертификаты), контрагенты/накладные/проводки, зарплата/мотивация/удержания, корпорация (дерево/настройки/нумерация/концепции), доставка (настройки/курьеры/клиенты/заказы), администрирование (лицензии/печ.формы/устройства), расписание, быстрое меню, план-факт, статус оплаты накладных. Полный список ключей — в `CONTRACT.md`.
  - **Operational / runtime** (горячий слой смены): `cashShift, orders, closedOrders, cashMovements, refunds, writeOffs, documents, banquets, closedShifts, stopList, messages` + счётчики последовательностей (`*Seq`).
- **Иерархия мультиарендности** уже есть: `CorpTree` = Юрлицо → Подразделение → Торговое предприятие (ТП) → Склад. Большинство данных должны **скоупиться по ТП** (и по юрлицу для бухгалтерии/ЭСФ).
- **Налоговая модель РК** зашита в данных: ставки ҚҚС на позициях (`vat: 16|0`), `vatBreakdown`, план счетов (`chartOfAccountsSeed`), правила проводок (`buildAutoPostings`), зарплатные налоги РК 2026 (`kzTax` в OfficeScreen).

## 3. Что должен произвести агент (ДЕЛИВЕРАБЛЫ)
Один связный документ `BACKEND_DESIGN.md` + DDL-миграции, со следующими разделами:

1. **Каталог сущностей.** Для каждой: имя таблицы, источник (тип в `types.ts` + ключ хранения), все поля (имя, тип PG, NULL/NOT NULL, дефолт), PK, **FK и связи** (1-1/1-N/N-N), enum-значения, инварианты. Имена полей — **1:1 с типами**, не переименовывать, не выдумывать.
2. **ER-диаграмма** (`mermaid erDiagram`) — все таблицы и связи.
3. **Мультиарендность/скоупинг.** Как ТП/юрлицо привязывается к каждой таблице (FK `trade_point_id` / `legal_entity_id`), что глобально (план счетов), что по-ТП.
4. **DDL для PostgreSQL** — `CREATE TABLE` + индексы (по FK, по датам для отчётов/движений, по фискальным номерам), стратегия миграций (EF Core Migrations или Flyway/DbUp — обосновать).
5. **API.** Два уровня, не ломая существующее:
   - **слой совместимости** ровно по `CONTRACT.md`: `GET/PUT/DELETE /api/config/:key`, `GET/PUT /api/runtime` (чтобы текущий фронт завёлся сразу через `httpRepository`);
   - **доменные эндпоинты** поверх (REST), смапленные на actions стора: смена (`shift.open/close`, X/Z), заказы (`order.create/pay/refund`), деньги (`cash.move`), склад (`stock.receive`, `doc.create`, `inventory`), накладные/оплаты (`invoice.create/pay`), лояльность (`loyalty.*`), доставка (`delivery.*`). Для каждого — метод, путь, тело/ответ, требуемое право.
6. **Авторизация (RBAC).** Модель из `lib/rights.ts`: пользователи↔должности↔права (`F_*/B_*/D_*`), скоуп прав, проверка на эндпоинтах. Аутентификация — PIN/карта на кассе, логин в офисе (предложить JWT + refresh).
7. **Бизнес-логика: сервер vs клиент.** Явно расписать по `lib/*`: что переносим на сервер (проводки/остатки/себестоимость/отчёты/задолженность — должны быть авторитетны на сервере), что можно оставить на клиенте (форматирование, чисто-презентационные срезы). Учесть, что списание по техкартам, начисление лояльности и фискализация — **транзакционные, только сервер**.
8. **KZ-специфика.** Где живут: ЭСФ (вх./исх.) + СНТ + Виртуальный склад, интеграция Webkassa/ОФД (онлайн-ФД, X/Z, ФН-ресурс), план счетов РК + выгрузка в 1С, зарплатные налоги (ИПН/ОПВ/ВОСМС/СО/ОПВР/ООСМС/СН). Что мок-able, что требует внешних интеграций (отметить как «адаптер»).
9. **Открытые вопросы / неоднозначности** (обязательный раздел — НЕ домысливать молча): напр. оплаты поставщикам как отдельная сущность (сейчас только флаг `invoice-paid`); «срок оплаты» накладной (в моке = дата+14 дн, нет поля); перемещение между складами при едином `stock` (мок-упрощение — нужен per-store остаток); мультивалютность; история цен/себестоимости (нужна для отчётов ABC/XYZ/изменение себест., которых в моке нет).

## 4. Правила для агента
- **Ничего не выдумывать сверх кода.** Сущности и поля берём из `types.ts`; если чего-то не хватает для реляционной модели (например, явные FK вместо матчинга по имени `supplierName`) — это **выносим в «Открытые вопросы»**, а не достраиваем молча.
- **Имена 1:1** с типами/ключами (легче миграция и поддержка).
- `CONTRACT.md` слегка отстаёт от кода в мелочах — **источник истины = код** (`types.ts` + `pos.ts`), контракт читать как карту, сверять с кодом.
- Сохранить **слой совместимости `PosRepository`** (config/runtime) — это путь «включить бэкенд за один день», доменные эндпоинты добавляются поверх.
- Учитывать **разницу слоёв**: runtime = частые записи в рамках смены (нужны транзакции, блокировки на оверселл/двойную оплату); config = редкие правки справочников.

## 5. Метод работы
1. Прочитать файлы из раздела 1 (полностью `types.ts`, `pos.ts`, `CONTRACT.md`; выборочно `mock/*`, `lib/*`).
2. Составить инвентарь ключей хранения → черновик таблиц (config-таблицы + runtime-таблицы).
3. Из `types.ts` заполнить поля и вывести FK по `*Id`/именам.
4. Наложить скоупинг по `CorpTree`.
5. Сгенерировать ERD + DDL + API-карту + RBAC + KZ-раздел + Открытые вопросы.
6. Вернуть `BACKEND_DESIGN.md` (+ `migrations/*.sql` или EF-модели).

> Опционально для приёмки (не для схемы): поднять `npm run dev`, войти Админ 0000 / Петров 1111, пройти ключевые флоу (открыть смену → заказ → оплата → закрытие; офис → накладная → оплата → проводки), сверить, что доменная модель покрывает реально происходящее. Скриншоты — в контекст агента.
