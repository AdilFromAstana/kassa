# iiko-pos — архитектура и принципы проекта

Главный документ проекта: **что это, как устроено, как связаны фронт и бэк, какие нюансы**. Читать перед работой.

---

## 1. Что это и зачем

**iiko-pos** — это **клон кассы iiko (iikoFront)** для сети общепита (🇰🇿 Казахстан). Цель — **воссоздать реальную кассу iikoFront 1:1**: те же экраны, кнопки, флоу, поведение.

Сейчас это **мок-фронт** (всё в браузере, без сервера). Дальше по плану:
- **Бэкенд на .NET** — заменит мок-слой реальным API;
- **Упаковка в Electron** — касса открывается как одна веб-страница на весь экран (киоск) на сенсорном терминале.

**Источник истины** для воссоздания — спецификация в `../iiko_spec/` (реверс реальной iiko: экраны, поля, права, КЗ-специфика). Главный файл — `iiko_spec/FULL_SPEC_FOR_AGENT.md`; по кассе — `FRONT_01/02/03`; по настройкам — `SETTINGS_REGIME_AND_PRECHECK.md`.

## 2. Связь фронт ↔ бэк ⭐ (главное)

Сейчас «бэкенд» проекта — это **zustand-store** [`src/store/pos.ts`](src/store/pos.ts) + статические данные [`src/mock/`](src/mock/). Это **умышленная граница**: вся бизнес-логика и доступ к данным сосредоточены в сторе, экраны только вызывают его методы и читают состояние.

**Когда появится .NET:** меняем ТОЛЬКО тело функций стора (мок → `fetch` к API). Экраны, роутинг, компоненты — не трогаем. Карта «функция стора → будущий эндпоинт»:

| Функция стора (сейчас мок) | Станет (бэкенд .NET) |
|---|---|
| `login(pin)` | `POST /auth/login` |
| `openPersonalShift / closePersonalShift` | `POST/DELETE /shifts/personal` |
| `openCashShift / closeCashShift` | `POST/DELETE /shifts/cash` (Z/X — на ФР) |
| `startOrder / addDish / setGuestNo / moveOrder…` | `POST/PATCH /orders…` |
| `pay / payByGuest` | `POST /orders/:id/pay` → **фискализация Webkassa** |
| `refundOrder / changePaymentType` | `POST /orders/:id/refund`, `PATCH …/payment` |
| `precheck` | `POST /orders/:id/precheck` (печать) |
| отчёты (Reports/X/Z) | `GET /reports/...` |
| справочники: меню, столы, сотрудники, типы оплат | `GET /menu`, `/tables`, `/staff`, `/payment-types` |
| банкеты/резервы, стоп-лист, внесения/изъятия | `GET/POST /banquets`, `/stop-list`, `/cash-movements` |
| склад: остатки, приход, инвентаризация, техкарты, списание при оплате | `GET /stock`, `POST /invoices` (приход), `POST /inventory`, `GET /tech-cards`; списание = серверный «Акт реализации» |

**Фискализация (важно):** реальные чеки печатает **ФР/Webkassa** на стороне терминала (драйвер) или .NET-бэка. Фронт лишь отправляет команды «оплатить», «пречек», «X/Z-отчёт», «чек коррекции», «возврат». Сейчас это мок — всплывающий тост «печать» (`src/lib/print.ts`) и сгенерированный номер ФД.

**Под Electron:** `npm run build` → `dist/` (статика, `base:'./'`, **HashRouter** — работает как `file://`). Electron-обёртка грузит `dist/index.html` в `BrowserWindow` (fullscreen/kiosk). Драйвер ФР/Webkassa подключается на стороне Electron/.NET.

## 3. Откуда берутся настройки (нюанс iiko)

Реальная касса iikoFront **сама ничего не настраивает** — она при синхронизации забирает настройки и права из **бэк-офиса** (iikoOffice локально на точке / iikoChain в центре сети) и рисует интерфейс соответственно. Поэтому одна и та же касса на разных точках выглядит по-разному.

Что приходит из офиса (детали — `iiko_spec/SETTINGS_REGIME_AND_PRECHECK.md`):
- **Режим заведения** — фастфуд / ресторан (задаётся на **группе терминалов**). Ресторан = столы/гости/пречек/деление; фастфуд = быстрый чек без пречека.
- **Права сотрудников (F_*)** — какие кнопки видны/доступны (Пречек, Возврат, Скидка, Открытие смены и т.д.).
- **Типы заказов, печать пречека, шаблоны чеков** и пр.

**В нашем моке (реализовано):**
- **Профиль заведения** = `establishment` в сторе (`src/store/pos.ts`): `mode` (restaurant/fastfood) + флаги (precheck, comments, courses, tab, mix, kitchenScreen, banquets, delivery, iikoCard, frCount). Дефолт — **🇰🇿 Ресторан**. Сохраняется в `localStorage` (`iiko-establishment`).
- Меняется на экране **«Настройки заведения»** (`/settings`, вход через `☰ → ИНСТРУМЕНТЫ → Настройки заведения`).
- **Видимость по профилю** уже привязана: режим ресторан/фастфуд → столы/гости/вкладки/деление/перенос/пречек; флаги precheck/comments/banquets → соответствующие кнопки. Хелпер в экранах: `const est = pos.establishment; const isRest = est.mode==='restaurant'`.
- **Права (F_*) пока НЕ реализованы** — отдельный слой поверх профиля (см. roadmap). Курсы/Коммент-кнопка/MIX/Таб как UI-кнопки ещё не построены (флаги есть, кнопок нет).

## 4. Принцип разработки: строго 1:1 с реальной iiko ⭐

UI делаем **идентично реальным скриншотам iikoFront**. Правила (нарушать нельзя):
- **не выдумывать** кнопки/элементы, которых нет на реальном экране;
- **не дублировать** (напр. ИТОГО уже в панели заказа — не повторять внизу);
- **не показывать вне режима** (Пречек только в ресторане);
- **не переставлять** (страницы меню I/II/III — в одном верхнем ряду с ← 🔍 🏠, а не сбоку);
- что есть в реале, но не помещается на кадр — прятать под реальные элементы (меню «…»), а не плодить кнопки;
- **иконки, а не эмодзи** — везде `lucide-react` (флаг 🇰🇿 → текстовый бейдж «KZ»);
- если для элемента нет реального скрина — **спросить/пометить, а не выдумывать**.

Рабочий цикл: пользователь присылает кадр реальной кассы → сверяем → правим точечно → проверяем сборкой и скриншотом (Playwright).

### 4.1 Тач-первый ввод (Electron-киоск на сенсорном мониторе) ⭐

Это веб-сайт, но он будет развёрнут в **Electron на сенсорных мониторах** — у кассира **нет физической клавиатуры**. Поэтому любое поле ввода открывает **экранный элемент ввода**, а не полагается на системную клавиатуру ОС:
- текст → полноэкранная сенсорная клавиатура `components/OnScreenKeyboard.tsx` (как в «ПОИСК ТОВАРА»);
- **время → `components/TimePickerModal.tsx`** (ЧЧ:ММ: цифры-ячейки + стрелки ±час/±мин + цифровая панель + «По умолчанию» / OK / Отмена) — 1:1 со скрином iikoFront; подключён в карточке резерва/банкета (тап по «Время:»);
- числа/количество → `NumPad`.

Правило: новые поля ввода в кассе НЕ используют «голый» `<input>` для ручного набора — вешаем соответствующий экранный пикер/клавиатуру. Физическая клавиатура/сканер ШК при этом тоже должны работать (реальный `<input>` под капотом, как в поиске).

## 5. Стек и структура

React 18 + Vite + TypeScript + Tailwind + Zustand + React Router (HashRouter). Иконки — lucide-react.

```
src/
├─ screens/        экраны (по одному на флоу)
├─ components/     TopBar, BackButton, NumPad, OnScreenKeyboard, ModifiersModal,
│                  TransferModal, SearchModal, CashMovementModal
├─ store/pos.ts    zustand — ВСЯ бизнес-логика и состояние (мок-«бэкенд»)
├─ mock/           menu.ts (меню+модификаторы+коды), data.ts (сотрудники, столы,
│                  типы оплат, ФР, явки, сообщения, банкеты)
├─ lib/            money.ts (₸ + ҚҚС 16%), print.ts (мок-печать = тост)
├─ types.ts        доменные типы
└─ router.tsx      HashRouter
```

Запуск:
```bash
npm install
npm run dev      # http://localhost:5180
npm run build    # dist/ (для Electron)
```
PIN (мок): Петров `1111` (Кассир/Менеджер), Иванова `2222` (Официант), Легасов `3333`, Админ `0000`.

## 6. Реализованные экраны и флоу

**Вход и смены:** PIN-вход → выбор должности → личная смена; доп. меню (4 колонки: Имя · ГОСТИ/ПЕРСОНАЛ · СЕРВИС · КАССА); открытие/закрытие кассовой смены (мастер с пересчётом и Z-отчётом); смена кассира; X-отчёт.

**Заказ (ресторан):** схема зала → стол → гости; **рабочий экран заказа** с вкладками гостей сверху, быстрым меню (3 страницы, группы→блюда), модификаторами, делением по гостям (ножницы → перенос гостю), переносом/объединением заказа, скидкой/надбавкой/пречеком под «…»; переключение/создание заказов в нижней панели (< +); **полноэкранный «ПОИСК ТОВАРА»** с сенсорной клавиатурой (ЙЦУКЕН/EN) + поиск по коду/штрихкоду.

**Оплата:** экран расчёта — типы оплаты, разбивка, сдача, оплата по гостям → **фискальный чек (мок Webkassa)** с БИН/ҚҚС 16%/ФД.

**Касса:** закрытые заказы + возвраты (частичный/полный, смена типа оплаты); открытые заказы; заказы закрытых смен (архив); внесение/изъятие денег; команды ФР; «Подробнее» (2 ФР + смена); чек коррекции.

**Сервис/персонал:** отчёты (~30 по разделам); стоп-лист (снятие блюд, отражается на заказе/поиске); банкеты и резервы (фильтры, дата, поиск, статусы) + карточка создания (КЛИЕНТ/РЕЗЕРВ, обязательные поля розовым); личная страница; редактировать явки; сообщения; дополнения/инструменты (+ переключатель режима).

**Демо-данные для показа без бэка (`src/mock/demo.ts`, управление в «Настройки заведения»):** генератор `buildDemo()` создаёт пачку **закрытых заказов** за «сегодняшний вечер» (время — относительно `Date.now()` при запуске: разные блюда/количества/цены/типы оплаты/номера ФД, ~8 ч назад → сейчас), несколько **открытых заказов** на столах (оплатить вживую) и внесение размена. По ним сразу доступны: чеки, **возвраты** (частичный/полный), смена типа оплаты, **отчёты** (X/045/048 считаются из закрытых заказов), закрытие смены. Кнопки «Сгенерировать 12/24/40» (`seedDemo`), «Очистить» (`clearDemo`) и тумблер **«Авто-наполнение при запуске»** (`setDemoAuto`, флаг localStorage `iiko-demo-auto`) — при включении касса сама наполняется при открытии (и открывает смену №108), что и нужно для показа в неизвестное заранее время. Демо НЕ списывает склад (остатки остаются полными для живого показа).

**Склад (по модели iiko, `/warehouse`, вход через ИНСТРУМЕНТЫ → «Товары и склады»):** на складе лежат **товары-ингредиенты** с остатком и себестоимостью за ед. (`src/mock/warehouse.ts`), у блюд — **техкарты (ТТК)** с нормой закладки (брутто) на порцию. При **оплате** заказа (`pay`/`payByGuest`) ингредиенты **списываются по техкарте** (аналог «Акта реализации») — остаток падает и сохраняется в localStorage (`iiko-stock`). **Себестоимость** блюда «*» = Σ(брутто × себестоимость ингредиента). Кончились ингредиенты → блюдо **авто-уходит в стоп** на кассе (плитка серая, бейдж «нет»; «N шт» при остатке ≤5). Экран — две вкладки: **Остатки на складах** (Приход = приходная накладная, Факт = инвентаризация, Сбросить) и **Технологические карты** (цена/себест./себест.%/доступно порций/состав). Услуги (Доставка, Пробковый сбор) техкарты не имеют — склад не трогают. Модификаторы пока не списываются (упрощение). Реальный складской контур (накладные/инвентаризация/акты) живёт в офисе → ляжет на .NET-бэк.

> Качество: ключевые флоу прогоняются Playwright-смоуками (вход→смена→заказ→оплата→чек→отчёты, деление по гостям, возвраты, новые экраны) — без ошибок. Каждая правка проверяется `npm run build` + скриншот.

## 7. Что НЕ сделано (roadmap)

1. **Права/видимость кнопок (F_*)** — движок «кнопка = режим × право × состояние» (как `iiko_spec/FRONT_02`). Сейчас всё видно всем.
2. **Electron-обёртка** — киоск-окно вокруг `dist/`.
3. **.NET-бэкенд** — заменить мок-функции стора на API (см. §2); реальная фискализация Webkassa.
4. **Офисная часть** (iikoOffice/iikoChain) — отдельный продукт; пока только спека.
5. Мелочи: некоторые поля карточек (Карта/Прочее/Доп.информация) пока косметические; банкет-режим печати по концепциям.

## 8. Связь со спецификацией

Проект делается по `../iiko_spec/` — реверс-спека реальной iiko (≈100 реальных скринов, КЗ-локализация, права, FRONT_*-кассовые сценарии, настройки ТП/режима). При сомнениях «как должно быть» — смотреть туда или просить кадр реальной кассы. Не выдумывать.
